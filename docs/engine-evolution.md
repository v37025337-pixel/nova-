# Развитие поискового движка в едином runtime

Версия 0.2 добавляет проверяемую мутацию **политики исполнения поиска**. Код
перехода, типовые ограничения и пространство мутаций написал разработчик.
NOVA сама выводит конкретную политику из AST своих действующих программ.
Внешняя модель не передаёт готовые решения задач и не выбирает победителя.

## Последовательность

1. Старый журнал полностью воспроизводится по прежней семантике. Разрешён только
   точный manifest канонической версии 0.1 и та же minor-версия Python.
2. `upgrade` добавляет событие с исходным head, обоими runtime и регрессией
   активных программ. Поколение и память не меняются. Автор этого изменения —
   разработчик; это не нативная мутация NOVA.
3. `evolve suite.json` регистрирует задачу типа ENGINE в общей очереди.
   Обычный `step` строит одну политику по частотам операций в активных генах.
4. Обучающий gate повторяет прежние задачи с памятью, существовавшей до их
   приёма. Собственное готовое решение задачи исключается из поиска. Требуются
   успех на всех задачах и строго меньше исполненных кандидатов суммарно.
5. Зафиксированная политика строит решения новых проверочных задач, получая
   только их `train`. Затем проверяются их `holdout` и все старые навыки.
6. Успех атомарно публикует новый геном с прежними программами и `engine`-геном.
   Неудача оставляет активный геном прежним. Повторное использование проверочных
   входов, включая переименование, запрещено. Решения проверки не наследуются.
7. Следующий `step` использует принятую стратегию для обычных задач. Смена
   политики разрешает новую попытку ранее исчерпанного поиска. При равном
   дефиците новые задачи имеют приоритет перед дорогой неудачной попыткой.

## Что наследуется

Геном версии 2 содержит прежние `bindings`, `genes`, хеш родителя и полный
проверенный `engine` с собственной идентичностью. Программные мутации сохраняют
эту политику. Откат к геному версии 1 возвращает прежний поиск без изменения
событий. Нумерация поколений общая для программ и движка; она не измеряет общий
интеллект. CODE, LOGIC, THINKING и INTELLIGENCE оставляют квитанции с общим
контекстом и причинными ссылками для каждого типа шага.

`adaptation.py` содержит чистые функции. У него нет своего цикла, базы или
mutable-состояния. Все регистрации, выбор, проверки и переключения проходят
через `Kernel`, один reducer, одну очередь и один SQLite-журнал.

## Границы и проверка

- Поиск ограничен 12 000 исполненных кандидатов, глубиной до 4, фронтом до 96
  выражений и бинарным пулом до 64. Типовые отсечения считаются отдельно.
- Политика меняет порядок и охват поиска, поэтому первый точный обучающий
  кандидат может отличаться. Свежая проверка и регрессия обязательны.
- Снижение числа исполнений измеряется на прежних обучающих задачах. Само по
  себе оно не доказывает пропорциональное ускорение по времени или общий интеллект.
- Кэш состояния сохраняет только уже проверенный префикс в памяти процесса.
  Хеши проверяются при каждом чтении; несовпадающий префикс воспроизводится заново.
  Холодный запуск и `verify` полностью пересчитывают решения и доказательства.
- Подмена исходников, генома, результата gate или migration-anchor отвергается
  даже после пересчёта хешей событий. От усечения хвоста защищает внешний head.
- Произвольная перезапись исходников, новые примитивы и смена Python не входят
  в нативное пространство мутаций. Поддерживается только переход 0.1 → 0.2.

Первый протокол продолжения поколения 8 находится в
`experience/engine-cycle-v2/protocol.json`. Новые данные — подготовленные
разработчиком синтетические текстовые, числовые и JSON-примеры. Они проверяют
конкретные свойства поиска; это не независимый benchmark общего интеллекта.

Существенные проверки: миграция без потери событий, прежняя исполнимость,
изменение политики, следующая задача, replay/restart/rollback, плохой holdout,
повторное использование данных, типовая семантика и подмена проверенного кэша.
Они находятся в `tests/test_engine_evolution.py` и прежнем наборе тестов.
